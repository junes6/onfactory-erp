# 인더필드 (InTheField)

식품제조사의 제품·업무·재고·공장·판매·인사를 하나의 흐름으로 연결하고, Claude 기반 AI가 정보 조회, 검증 제안, 업무 초안 작성을 지원하는 통합관리 웹시스템입니다.

## 현재 구현된 기능

- **AI 업무허브**: 제품·재고·판매채널·열린 업무 컨텍스트를 전달하는 Claude 채팅과 업무 생성
- **개인화 메인화면**: AI·일정·내 업무·알림·업무 바로가기 위젯의 노출, 순서와 너비를 사용자별로 편집
- **업무 바로가기**: 네이버·나라장터 기본 링크와 회사/개인 업무 URL을 아이콘으로 추가·수정·삭제
- **사내 메신저 · 알림**: 오른쪽 상단 메신저에서 중복 없는 1:1 대화, 메시지별 읽음 상태, 대화 나가기·관리자 삭제를 처리하고 알림은 별도 패널에서 확인
- **개발운영진 지원 채널**: 모든 고객사에 변경 불가 시스템 대화를 제공하고 첫 문의는 플랫폼 CS 티켓으로 자동 등록, 후속 메시지·운영자 답장·첨부파일을 같은 요청에 누적
- **공유 일정**: 전사·부서·개인 범위 일정 등록·수정·삭제, 담당부서 관리, 승인 휴가의 사유 비노출 공유
- **업무지시 · 결재**: `업무요청 → 수행중 → 결재대기 → 결재완료` 흐름, 완료 결과·증빙 첨부, 코멘트 승인·수정 요청 이력
- **반복 업무**: 매주 지정 요일, 매월 특정일, 매월 마지막 주 특정 요일 자동 업무 생성과 중복 방지
- **일일업무일지**: 업무 내용·이슈·다음 계획·첨부파일 작성, 임시저장, 관리자 코멘트 승인·반려와 보완 재제출
- **제품 통합관리**: 제품 등록·편집, 표시·법규 검증, 판매채널, 재고 LOT를 제품 중심의 4개 탭으로 관리
- **판매채널 통합**: 쿠팡·네이버·G마켓·자사몰·11번가·SSG 등 채널 추가·해제, 공식 판매자 API 설정, 배송 주문 CSV, 택배사·송장 등록과 인쇄
- **재고 · 공장관리**: 창고 등록·수정, LOT 입출고·증빙 등록, 도면 없이 만드는 공장 블록의 드래그 이동·마우스 크기조절·패닝·휠 확대축소
- **인사 · 계정**: 내 휴가 잔여·사용·총량, 시작·종료일 기반 평일 자동계산, 결재자 지정, 월별/연초/수동 발생정책과 관리자 원장
- **기업 자료실**: 고객사별 실제 파일 업로드·다운로드, 전사/부서/계정 열람권한, AI 메타데이터 검색, WebDAV·SMB·S3 방식 NAS 연결 준비
- **식품안전 · 인증**: HACCP, 품목제조보고, 자가품질검사, 표시 검토, 위생교육, 검교정의 기한·증빙·체크리스트와 AI 우선조치 검토
- **백업 이중화**: 야간 배치가 업무 데이터 덤프를 NAS 경로에 세대별로 보관하고, 같은 덤프와 파일 원본을 S3 호환 버킷에 미러합니다. 실행 주기·대상·보관 세대 수는 환경변수이며, 실패하면 플랫폼 콘솔에 경고와 마지막 성공 시각이 표시됩니다
- **내 판단 기록 (개인 지식 코어)**: 테넌트 격리 위에 계정 소유 계층을 둡니다. 승인 큐에서 같은 방향으로 세 번 이상 고치면 규범 후보가 올라오고, 승인하면 원칙 문장·근거 결정 3건·신뢰도·유효기간(180일)을 담은 규범 카드로 확정됩니다. 확정 카드는 이후 AI 답변에 컨텍스트로 주입되고, 확신도가 기준(기본 60%)보다 낮으면 추측 대신 '판단 근거가 부족합니다'로 남기고 'AI가 모르는 것'에 기록합니다. 다른 계정은 API를 직접 불러도 존재 자체를 볼 수 없습니다
- **대표 브리핑**: 고객사 관리자의 AI 업무허브 최상단에 아침판(그날 첫 접속)·저녁판(17시 이후) 브리핑을 만듭니다. 아침판은 승인 대기 상위 1건·오늘 마감·센티널 경고·어제 완료·오늘의 기회를, 저녁판은 오늘 한 일·미결 이월·내일 첫 액션을 한 줄씩 근거 링크와 함께 보여 주고, 데이터가 없는 항목은 줄을 만들지 않습니다. 스냅샷은 digests에 남아 날짜로 다시 볼 수 있습니다
- **외부 기회 감시**: 외부 워커가 인제스트 API로 밀어넣은 입찰·지원사업 공고를 테넌트 감시 설정(키워드·지역·금액 하한·판정 점수 기준)으로 걸러, 기준을 넘은 건만 승인 큐에 제안으로 올립니다. 기준 미만은 목록에만 남습니다
- **렌즈 (파일 AI 분석)**: 자료실·인증·지식재산 파일 카드의 [AI에게 물어보기]로 오른쪽 패널을 열고 핵심만·리스크 점검·업무 추출 렌즈를 실행합니다. 결과에는 원문 근거가 붙고, 업무 추출은 [승인 큐로 보내기]로 기존 제안 흐름에 올라갑니다. 렌즈 정의(이름·지시문·출력형식·대상 파일유형)는 코드가 아니라 테넌트 DB 레코드이며 관리자가 직접 추가합니다
- **문서 자동 입력**: 인증서·특허증·계약서를 올리면 명칭·번호·발급일·만료일·금액을 읽어 원문 근거와 함께 확인 화면에 제시하고, 사람이 승인·수정한 값만 대장에 채움(등록은 파일 업로드부터 시작하며 자동 확정 없음)
- **세무 대응**: 업종·법인 구분에 따라 부가가치세·원천세·법인세(중간예납 포함)·지급명세서·보수총액 신고 일정과 준비 서류를 시스템이 먼저 제시하고(등록 없이 신규 고객사도 남은 일정 표시), 증빙을 분류·증빙일자와 함께 상시 축적한 뒤 기간 하나만 골라 압축본과 목록표(manifest.csv·전달요약.txt)를 만들고 전달 이력을 남김
- **개인 메뉴 편집**: 왼쪽 업무 메뉴의 표시 이름, 노출 여부와 순서를 계정별로 조정
- **통합 관리자**: 햇살바다와 포항시수산가공협동조합을 별도 플랫폼 콘솔에서 관리하고 CS·연동·지원 세션 감사 확인
- **비용 · 포인트**: AI 호출 전 한도 예약, 실제 입출력 토큰 확정, 모델별 환산율·요금제·고객사 배정, 저장공간 일별 스냅샷과 월별 불변 청구 원장을 플랫폼에서 관리
- **직원 성과**: 테넌트 관리자 전용 월간·분기 리포트에서 업무 완료·기한 준수·보완·처리시간·일지·결재응답 지표와 근거 업무가 연결된 4줄 AI 요약 확인
- **승인형 지원 세션**: 플랫폼 운영자가 고객사로 직접 전환하지 않고, 고객사·CS 티켓·읽기 전용 범위·15/30분 제한을 지정해 승인 요청
- **로그인 · 개인설정**: HttpOnly 세션, 고객사/플랫폼 역할 분리, 승인 대기 계정, 비밀번호 찾기 화면, 라이트·다크·시스템 테마, 3단계 글자 크기
- **공용 버튼 컴포넌트**: 모든 화면의 버튼이 `Button`/`IconButton` 하나를 쓰고 톤(primary·secondary·ghost·quiet·danger)과 크기만 고릅니다. 화면별 버튼 스타일 정의는 두지 않으며 `pnpm verify:button`이 이를 강제합니다
- **반응형 UI**: 데스크톱·태블릿·모바일 레이아웃, 최소 14px 기본 글자, 키보드 포커스 순환과 모달 접근성

예시 제품은 제공된 햇살바다 상품군(멍게젓, 붉은대게라면, 육수다시 선물세트, 바이오 미스틱)을 사용합니다.

## 로컬 실행

Node.js 20 이상과 pnpm을 준비합니다. 운영과 동일한 권장 경로는 Postgres이며, 로컬 Supabase를 사용하려면 Docker Desktop도 필요합니다.

~~~bash
pnpm install
cp .env.example .env.local
pnpm db:start
pnpm db:reset
DEMO_SEED_PASSWORD='12자 이상의 임시 암호' pnpm db:seed -- --base-date=2026-08-20
pnpm dev
~~~

PowerShell에서는 seed 실행 전에 `$env:DEMO_SEED_PASSWORD='12자 이상의 임시 암호'`를 설정합니다. Docker가 없는 이관 전 로컬 환경은 `.env.local`에 `STORE_BACKEND=json`, `STORE_JSON_READONLY=false`를 **명시한 경우에만** 기존 JSON 파일에 쓸 수 있습니다. Postgres 연결 실패로 자동 전환되는 JSON fallback은 데이터 보호를 위해 읽기 전용입니다.

브라우저에서 [http://localhost:5173](http://localhost:5173)을 엽니다. pnpm dev 한 명령으로 Vite 웹앱과 로컬 API 서버가 함께 실행됩니다.

체험 계정 이메일은 아래와 같으며, Postgres seed에서는 `DEMO_SEED_PASSWORD`로 지정한 임시 암호를 사용하고 첫 로그인 후 변경합니다. 레거시 JSON 데모의 암호는 기존 `demo1234`입니다.

- 햇살바다 관리자: `admin@sunsea.co.kr` / `demo1234`
- 햇살바다 일반 직원(생산 반장): `taesik.oh@sunsea.co.kr` / `demo1234`

- 인더필드 플랫폼 운영자: `operator@onfactory.co.kr` / `demo1234` (기존 계정 이메일은 데이터 연결 보존을 위해 유지합니다)
- 승인 대기 계정 확인용: `newstaff@sunsea.co.kr` / `demo1234`

제품·업무·반복규칙·일정·메신저·일지·휴가원장·창고·입출고·판매채널·공장 배치·인증대장은 로그인한 고객사 범위로 Postgres의 도메인별 정규 테이블에 저장됩니다. 기업 자료 메타데이터는 `items`, 원본 파일은 로컬 또는 S3 어댑터에 저장됩니다. 같은 고객사 계정으로 접속하면 브라우저가 달라도 권한 범위에 맞는 동일한 공유 상태를 불러옵니다.

Claude API 키가 없어도 전체 UI와 데모 응답을 확인할 수 있습니다. 실제 Claude를 연결하려면:

~~~powershell
Copy-Item .env.example .env.local
~~~

그다음 .env.local의 ANTHROPIC_API_KEY에 서버용 키를 입력하고 pnpm dev를 다시 실행합니다. 키는 브라우저 번들에 포함되지 않고 로컬 API 서버에서만 사용합니다.

자료 원본은 `FILE_STORAGE_BACKEND=local|s3`로 전환합니다. 로컬은 `FILE_STORAGE_LOCAL_DIRECTORY`, MinIO·S3 호환 저장소는 `S3_BUCKET`, `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`를 설정합니다. 업로드·다운로드·삭제·서명 URL은 동일한 저장소 인터페이스를 사용하므로 라우트 코드를 바꾸지 않습니다.

## 검증과 운영 실행

~~~bash
pnpm test:server
pnpm test:pg
pnpm verify
pnpm build
pnpm start
~~~

`pnpm verify`는 런타임 데모 분리, 20개 정규 테이블(성과 설정·월별 성과 스냅샷 포함)과 코어 테이블 계약, 날짜 표시 유틸 사용, CSS 하드코딩 색·타입·간격·모서리·그림자 위반 0건, 그리고 버튼 톤 단일화(공용 `src/components/ui/Button.tsx`만 사용하고 화면 CSS는 버튼 모양을 정의하지 않음)를 검사합니다.

비용·포인트 테이블은 `supabase/migrations/20260821000000_billing.sql`에 있으며 `pnpm db:reset` 또는 Supabase migration 적용 시 함께 생성됩니다. 모델 환산율·요금제·기본요금은 모두 0과 `미확정`에서 시작하므로 운영자가 콘솔에서 확정하기 전에는 임의 가격을 표시하지 않습니다. 매일 자정(KST) 저장공간을 수집하고 전월 원장을 멱등 확정하며, 이미 확정된 월은 이후 요율 변경으로 다시 계산하지 않습니다.

성과 리포트는 고객사 관리자가 가중치를 합계 100%로 설정하고 수동 재생성할 수 있습니다. 매월 첫 조회 또는 정기 실행에서 전월 스냅샷을 생성하며, 직원 본인 공개는 기본 비공개입니다. 공개하더라도 직원은 자기 리포트만 볼 수 있고 고객사 간·직원 간 조회는 서버 권한 검사와 RLS 정책으로 차단합니다.

실제 Postgres 통합 검증은 업무용 DB가 아닌 전용 테스트 DB를 `DATABASE_URL`로 지정한 뒤 `pnpm test:pg:e2e`를 실행합니다. 현재 장비처럼 Docker가 없으면 `pg-mem` 통합 테스트만 실행되며 Supabase 기동 검증은 생략됩니다.

- 개발 웹: http://localhost:5173
- 개발 API: http://127.0.0.1:8787
- 운영 통합 서버: 기본 http://127.0.0.1:8787

## 업데이트와 데이터 보존

코드 업데이트 전에 고객사 공유 데이터와 자료 원본을 함께 백업합니다.

~~~bash
pnpm backup:data
~~~

생성된 백업은 `server/backups/onfactory_날짜_시간/`에 저장됩니다. 이후 코드를 업데이트하고 `pnpm install`, `pnpm build`를 실행해도 `server/data/`는 삭제하거나 초기화하지 않습니다.

기존 JSON을 Postgres로 처음 이관할 때는 서버를 중지하고 기준일을 명시합니다. 스크립트는 원본을 수정하지 않고 타임스탬프 백업을 만든 뒤, 같은 트랜잭션 안에서 tenant/key별 원본·적재 건수를 검증합니다.

~~~bash
pnpm db:migrate:json -- --source=server/data/workspace-state.json --base-date=2026-08-20
~~~

불일치가 있으면 트랜잭션을 롤백하고 비정상 종료합니다. 업데이트 후에는 정규 테이블과 S3/로컬 파일 저장소를 함께 백업하며, JSON fallback을 운영 쓰기 저장소로 되돌리지 않습니다.

장애 복구가 필요할 때는 서버를 중지하고, 현재 데이터도 먼저 백업한 뒤 명시적으로 복원합니다.

~~~powershell
$env:CONFIRM_RESTORE='YES'
pnpm restore:data -- --from=server/backups/onfactory_YYYY-MM-DD_HH-MM-SS-sss
~~~

운영 환경에서는 `ONFACTORY_DATA_DIRECTORY` 또는 `WORKSPACE_STORE_FILE`을 배포 디렉터리 밖의 영구 볼륨으로 지정하고, 해당 볼륨을 정기 스냅샷 대상으로 등록하세요.

Sites 배포에서는 코드와 운영 데이터를 분리합니다. 업무·일정·메신저·설정은 D1에, 실제 첨부 파일과 공장 도면은 R2에 유지되므로 새 버전을 배포해도 기존 자료를 초기화하거나 덮어쓰지 않습니다. `worker/initial-workspace-state.json`은 비어 있는 신규 배포를 위한 최초 예시값으로만 사용됩니다. 배포 전에는 `ERP_SEED_PASSWORD`를 12자 이상의 Sites secret으로 설정해야 하며, 초기 계정은 첫 로그인에서 비밀번호 변경을 요구합니다.

### Sites 운영 계정 1회성 복구

통합 운영자 또는 3D뮤즈 관리자 계정의 비밀번호를 알 수 없어 로그인할 수 없을 때는 계정을 삭제하거나 D1의 업무 데이터를 초기화하지 않습니다. Sites의 배포 환경에 복구 revision을 등록하고, 두 임시 비밀번호는 **secret**으로 등록한 뒤 새 버전을 배포합니다.

- `ERP_ACCOUNT_RECOVERY_VERSION`: 공백이 아닌 새 복구 revision 문자열입니다. `YYYYMMDD-N` 형식을 권장합니다. 같은 문자열은 다시 적용되지 않으므로 재복구 때마다 이전과 다른 문자열로 바꿉니다.
- `ERP_OPERATOR_RECOVERY_PASSWORD`: 통합 운영자에게 발급할 12자 이상의 강한 임시 비밀번호입니다.
- `ERP_3DMUSE_RECOVERY_PASSWORD`: 3D뮤즈 관리자에게 발급할 12자 이상의 강한 임시 비밀번호입니다.

두 임시 비밀번호는 `.env.local`, 문서, 이슈, 채팅 또는 Git에 기록하지 말고 Sites secret 저장소에만 입력합니다. 세 값을 모두 설정한 배포가 처음 실행될 때 대상 계정의 인증 정보만 한 번 갱신되고 기존 세션은 만료됩니다. 고객사, 업무, 일정, 메신저, 파일 메타데이터와 R2 원본은 변경하지 않습니다. 복구된 계정은 임시 비밀번호로 로그인한 직후 새 비밀번호 설정 화면으로 이동하며, 변경을 마쳐야 워크스페이스를 사용할 수 있습니다.

복구 후에는 두 계정의 로그인과 첫 로그인 비밀번호 변경을 확인합니다. 이후 코드만 다시 배포해도 같은 `ERP_ACCOUNT_RECOVERY_VERSION`은 재실행되지 않습니다. 다시 복구해야 할 때에는 새 임시 비밀번호 두 개를 secret에 교체하고 복구 revision도 이전과 다른 문자열로 바꾼 다음 배포합니다. 운영 비밀번호나 임시 비밀번호의 실제 값은 배포 로그와 완료 보고서에도 남기지 않습니다.

## 백업 이중화와 복구

한쪽 저장소가 통째로 사라져도 반대편에 **전일자까지** 남도록 교차 보관합니다.

| 무엇을 | 어디에 | 언제 |
| --- | --- | --- |
| 업무 데이터 덤프(`server/data` 전체) | NAS 경로 `BACKUP_NAS_DIRECTORY` | 매일 `BACKUP_SCHEDULE_HOUR`시(KST), 이후 `BACKUP_INTERVAL_HOURS`마다 |
| 같은 덤프 + 파일 원본 | 클라우드 버킷 `BACKUP_CLOUD_BUCKET` (S3 호환) | 같은 사이클에서 이어서 |

~~~bash
BACKUP_ENABLED=1                       # 배치 사용 여부
BACKUP_NAS_DIRECTORY=/mnt/nas/inthefield-backup
BACKUP_CLOUD_BUCKET=inthefield-backup  # 비우면 NAS만 보관
BACKUP_CLOUD_PREFIX=inthefield-backup
BACKUP_RETENTION_GENERATIONS=14        # 보관 세대 수
BACKUP_SCHEDULE_HOUR=3                 # 첫 실행 시각 (KST)
BACKUP_INTERVAL_HOURS=24               # 반복 주기
~~~

클라우드 버킷은 파일 저장소와 같은 S3 설정(`S3_ENDPOINT`·`S3_REGION`·`S3_ACCESS_KEY_ID`·`S3_SECRET_ACCESS_KEY`)을 씁니다.

플랫폼 콘솔 **연동 상태** 화면의 [백업 이중화] 패널에서 마지막 성공 시각·최근 세대·연속 실패 횟수를 확인합니다. 실패하면 같은 자리에 경고가 뜨고 감사 로그에 "백업 경고"로 남습니다. NAS는 성공했는데 클라우드 미러만 실패한 경우에도 경고를 띄우되 마지막 성공 시각은 갱신합니다 — 복구 가능한 사본이 한 벌은 남았기 때문입니다.

### 복구 절차

1. **서버를 멈춥니다.** 복구 중 쓰기가 섞이면 어느 쪽이 정본인지 알 수 없게 됩니다.
2. **현재 데이터부터 백업합니다.** 망가진 상태라도 원본은 남겨 둡니다.
   ~~~bash
   pnpm backup:data
   ~~~
3. **어느 세대로 되돌릴지 고릅니다.** NAS의 `BACKUP_NAS_DIRECTORY`에서 `inthefield_YYYY-MM-DD_HH-MM-SS-mmm` 폴더를 확인하고, 각 폴더의 `BACKUP_INFO.json`에서 생성 시각과 스키마 버전을 봅니다.
4. **NAS가 살아 있으면 NAS에서 복원합니다.**
   ~~~powershell
   $env:CONFIRM_RESTORE='YES'
   pnpm restore:data -- --from=/mnt/nas/inthefield-backup/inthefield_2026-08-31_03-00-00-000
   ~~~
5. **NAS가 소실됐으면 클라우드 버킷에서 같은 세대를 내려받아 같은 명령으로 복원합니다.** 버킷의 객체 키는 `<BACKUP_CLOUD_PREFIX>/<세대>/<원본 상대경로>` 형태이므로, 세대 폴더 하나를 통째로 받아 로컬 경로로 지정하면 됩니다.
6. **서버를 다시 켜고** 로그인 → 업무 목록 → 파일 다운로드까지 한 번씩 확인합니다.
7. **콘솔에서 다음 백업이 성공하는지 확인합니다.** 연속 실패 횟수가 0으로 돌아와야 복구가 끝난 것입니다.

Postgres를 운영 저장소로 쓰는 배포에서는 3~5단계 대신 관리형 데이터베이스의 PITR 스냅샷을 사용하고, 이 배치는 파일 원본(R2/S3)과 설정 스냅샷의 이중화만 담당합니다.

## 외부 기회 인제스트 API

입찰·지원사업 공고의 **수집과 판정은 이 저장소 밖의 워커**가 담당합니다. 판정 프롬프트를 고칠 때마다 제품 전체를 다시 배포하지 않기 위해서입니다. 인더필드는 워커가 밀어넣은 결과를 받아 보여 주고, 임계값을 넘은 건만 기존 승인 큐에 올립니다.

배포 환경에 `OPPORTUNITY_INGEST_TOKEN`(32자 이상 권장)을 secret으로 설정하면 인제스트가 열립니다. 설정 전에는 이 경로가 503으로 닫혀 있습니다.

~~~
POST /api/opportunities/ingest
Authorization: Bearer <OPPORTUNITY_INGEST_TOKEN>     (또는 X-Ingest-Token 헤더)
Content-Type: application/json

{
  "opportunities": [
    {
      "tenantId":  "TENANT-XXXX",              // 필수 · 대상 고객사
      "noticeNo":  "G2026-0001",               // 필수 · 공고번호 (같은 출처+번호는 재등록되지 않음)
      "title":     "학교 급식 식자재 납품",       // 필수
      "source":    "나라장터",                   // 선택 · 기본값 "외부"
      "agency":    "○○교육청",                  // 선택
      "deadline":  "2026-10-15",               // 선택 · 실제 달력에 있는 YYYY-MM-DD만 저장
      "amount":    240000000,                  // 선택 · 원 단위 정수
      "link":      "https://www.g2b.go.kr/...", // 선택 · http/https만 저장
      "score":     0.82,                       // 선택 · 0~1 판정 점수 (없으면 임계 미만 취급)
      "rationale": "감시 키워드 \"급식\" 일치"    // 선택 · 판정 근거
    }
  ]
}
~~~

한 번에 최대 50건입니다. 응답은 처리 결과의 집계입니다.

~~~json
{ "accepted": 2, "queued": 1, "belowThreshold": 1, "duplicate": 0, "unknownTenant": 0 }
~~~

- `queued` — 테넌트 설정의 판정 점수 기준과 금액 하한을 넘어 **승인 큐에 `opportunity` 제안으로 올라간 건**입니다. 관리자가 ✓승인하면 검토 업무가 만들어지고, ✗거절은 학습 신호로 남습니다.
- `belowThreshold` — 기준 미만이라 목록에만 남긴 건입니다. 승인 큐에는 올리지 않습니다.
- `duplicate` — 같은 출처·공고번호가 이미 있는 건입니다.
- `unknownTenant` — 존재하지 않는 고객사입니다.

| 상태 코드 | 오류 코드 | 뜻 |
| --- | --- | --- |
| 401 | `INGEST_UNAUTHORIZED` | 토큰이 없거나 일치하지 않음 |
| 400 | `INVALID_OPPORTUNITY` | 공고번호·제목·대상 테넌트 누락 |
| 413 | `OPPORTUNITY_BATCH_TOO_LARGE` | 한 번에 50건 초과 |
| 404 | — | 보낸 건이 모두 존재하지 않는 고객사 |
| 503 | `INGEST_NOT_CONFIGURED` | `OPPORTUNITY_INGEST_TOKEN` 미설정 |
| 500 | `OPPORTUNITY_WRITE_FAILED` | 저장 실패 (아무 것도 반영되지 않음) |

감시 키워드·지역·금액 하한·판정 점수 기준은 고객사 관리자가 **AI 제안 검토** 화면의 [기회 감시 설정]에서 정합니다. 초기값은 업종 모듈이 채웁니다 (식품제조: 급식·수산물 납품·식품 R&D / IT서비스: 콘텐츠·소프트웨어 개발 용역·안전교육).

## 실제 운영 연동 전 확인

이 저장소만으로 로컬 업무 흐름과 고객사별 공유 저장은 실행할 수 있습니다. 다만 외부 서비스는 해당 사업자의 자격정보가 있어야 실제 데이터가 들어옵니다.

- 쿠팡·네이버·G마켓 등: 판매자 API/OAuth 앱, 웹훅 URL, 상품코드 매핑 권한
- 회사 NAS: WebDAV/SMB/S3 서비스 계정과 Secret Vault, 사내망 접근 에이전트
- 비밀번호 재설정·초대 메일: 회사 메일 발송 서비스와 도메인 인증
- 운영 DB·백업: 조직의 보존기간, 개인정보 처리, 장애복구 정책에 맞춘 관리형 데이터베이스
- 지원 세션 감사: 고객 승인 채널, JIT 권한 발급·만료, 변경 불가 감사 저장소

현재 제품·매출·고객사·CS 수치는 제공된 화면을 검증하기 위한 예시 데이터이며, 외부 채널 자격정보를 넣었다고 오인하지 않도록 UI와 운영 데이터를 분리했습니다.
